# 代码审查

## 确定范围
- 没有指定范围时，默认审查未提交的改动：先 `git_status`，再 `git_diff`（staged 和 unstaged 都要看）。
- 对每个改动的文件，用 `read_files` 读取足够的上下文。只看 diff 容易漏掉调用方和不变量。
- 函数签名、导出或公共接口有变化时，用 `lsp` incoming_calls/references 找出所有调用方。

## 检查清单（按优先级）
1. **正确性**：逻辑错误、边界条件（空值、空数组、0、超长输入）、off-by-one、异常路径、并发和竞态、资源泄漏（句柄、定时器、子进程）、async 忘了 await。
2. **安全**：注入（shell、SQL、路径穿越）、未校验的外部输入、密钥硬编码、日志泄露敏感信息、权限检查缺失、不安全的反序列化。
3. **兼容性**：破坏性的 API/配置变更、数据迁移、跨平台差异（Windows 路径和 shell、换行符）。
4. **性能**：热路径上的 O(n²)、循环里做 IO、不必要的全量读取、没有上限的缓存或队列。
5. **可维护性**：命名、重复代码、过长的函数、魔法数字、错误信息是否可操作、改动是否附带测试。

## 原则
- 只报**真实存在**的问题，每条都要指到具体的 `文件:行号`，并说明为什么会出问题。
- 不确定的问题标成"疑问"，不要当作结论。
- 纯风格偏好（格式、个人习惯）最多一句带过，除非违反了项目已有的约定。
- 每个问题都给出具体改法，最好附上建议的代码片段。
- 做得好的地方可以简短提一句，但不要凑数。
- 默认只审查不修改。用户要求修复时，再用 `apply_patch` 逐条修改。

## 输出格式
```
总结：<1–2 句，整体评价，是否建议合并>

🔴 必须修复
- file.js:42 — <问题>。<原因>。建议：<改法>

🟡 建议修改
- ...

🔵 小问题 / 疑问
- ...
```
某个级别没有问题就省略那一节。
