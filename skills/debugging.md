# 系统化调试

目标：用最少的改动修复**根因**，而不是把症状压下去。每一步都要有证据。

## 1. 复现
- 先弄清楚：期望行为是什么，实际行为是什么，触发条件是什么。
- 找到最短的复现路径（命令、输入、测试）。复现不了就先别改代码，回去问用户要更多信息（完整报错、版本、步骤）。
- 用 `run_command` 实际跑一遍，把原始输出记下来。

## 2. 收集证据
- 完整读一遍报错和堆栈，找到**第一个**出错的位置，不要只看最后一行。
- 用 `get_diagnostics` 查看编译器/类型检查的结构化错误。
- 用 `lsp` 跳到定义、查看引用，搞清数据从哪里来、流向哪里。
- 用 `git_diff` / `git_status` 看最近改过什么。"之前好好的"类问题，大多出在最近的改动上。

## 3. 提出假设并验证
- 列出 1–3 个可能的根因，按可能性排序。
- 每个假设都设计一个能**证伪**它的小实验：加日志、写断言、构造最小输入、临时注释掉某段逻辑。
- 一次只改一个变量。实验结果不支持假设，就换下一个，不要硬套。
- 发现根因后，能用一句话说明"为什么会出错"，才算真正找到。

## 4. 修复
- 做最小的、针对根因的修改，用 `apply_patch`，改之前先 `read_files`。
- 同一个错误模式可能出现在别处，用 `search_files` / `lsp references` 检查。
- 不要顺手重构无关代码，那样会让 diff 难以审查。

## 5. 验证
- 重新跑第 1 步的复现，确认问题已经消失。
- 能写回归测试的话就写一个：修复前失败，修复后通过。
- 跑一遍相关的已有测试，确认没有带来新问题（用户明确不让跑的除外）。
- 把临时加的日志/调试代码清理掉。

## 汇报格式
```
根因：<一句话>
证据：<关键日志/输出/代码行>
修复：<改了哪些文件、改了什么>
验证：<跑了什么，结果如何>
遗留风险：<没覆盖到的情况，没有就写"无">
```
