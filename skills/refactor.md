# 安全重构

核心约束：**外部可观察的行为不变**。行为变更（修 bug、加功能）和重构要分开做，不要混在同一个改动里。

## 1. 摸清现状
- 用 `get_file_outline` 查看目标文件的结构，再用 `read_files` 读取相关部分。
- 用 `lsp` references/incoming_calls 找出所有使用方，包括动态调用、字符串引用和配置里的引用（这些要用 `search_files` 补查）。
- 先确认这些都是公共接口：导出、命令 ID、配置键、工具名、文件格式。它们默认**不能改**，确实要改就先问用户。

## 2. 建立安全网
- 找到能覆盖目标代码的测试并运行，记录基线结果。
- 没有测试时，先补最小的特征测试（记录当前的输入和输出），或者和用户约定手动验证的步骤。
- 用 `set_todos` 把重构拆成若干步，每一步都可以单独验证。

## 3. 小步修改
每一步只做一种变换，常见的有：
- 改名（用 `lsp` rename 或者全量搜索替换，确保没有漏掉）
- 提取函数/模块，内联无用的中间层
- 用提前 return 减少嵌套，拆分过长的条件表达式
- 合并重复代码（至少出现 3 次再抽象，不要过早抽象）
- 把魔法数字换成命名常量
- 删除确认没有引用的死代码

每一步结束后：
- 运行 `get_diagnostics`，确保没有新增错误。
- 运行测试，结果应和基线一致。
- 失败了就回退这一步，找到原因再继续，不要在失败状态上叠加新的修改。

## 4. 收尾
- `git_diff` 通读一遍，确认没有夹带行为变更和无关的格式化。
- 汇报时写明：改了什么结构、为什么这样更好、怎么验证行为不变、有哪些公共接口刻意没动。

## 禁忌
- 不要一次性大规模改写整个文件。
- 不要为了"以后可能用到"引入抽象层。
- 不要在重构中顺手改错误文案、默认值、日志格式，这些都是行为。
